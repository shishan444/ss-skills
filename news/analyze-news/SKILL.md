# 新闻深度理解编排

## 核心原则

把新闻理解成一个受证据约束的问题世界，不把它扩写成一篇更长的摘要。

使用最小三角色结构：

- 当前主 Agent 作为 Master，负责边界、任务、研究包、门禁和最终报告；
- `news_researcher` 只负责事实与来源，调用 `$article-research`；
- `news_analyst` 只负责因果、局势与影响，调用 `$look-think`。

两个子 Agent 必须串行运行，任一时刻只启动一个。子 Agent 不得继续派生 Agent。Master 是共享研究包的唯一写入者；子 Agent 只可写入父任务指定的增量文件和取证材料。

启动命名自定义 Agent 时必须使用 `fork_turns="none"`，不要继承完整会话历史；把任务合同、增量文件路径和必要约束全部写进派发消息。子 Agent 把完整结果写入增量文件，只在消息中返回状态和路径；Master 读入文件后立即结束该线程，再启动下一个角色。这样既避免历史污染，也避免大段 JSON 回传拖住交接。

Master 分开记录两类预算：`followup_rounds` 约束内容补查，`delivery_recoveries` 约束运行时交付恢复；二者都不得超过 1，且交付恢复不能重置来源预算、补查预算或扩大原任务范围。

## 开始前

完整读取 [research-packet.md](references/research-packet.md)，并以 [research-packet.template.json](assets/research-packet.template.json) 建立研究包。

在 `works/tmp/` 下为本次任务建立独立目录，命名为 `yyyymmddhh-新闻分析`；把研究包、子任务、原始返回和验证结果放入其中。若同名目录已存在，使用更具体且不超过六个字的任务关键词，避免覆盖。

输入缺少 URL 但新闻对象明确时，按主题研究；只有不同解释会改变“研究的是哪件事”时才询问用户。记录 `as_of`，后续所有“当前”均以它为准。

## 执行流程

### 1. 建立研究任务

把用户输入转换为一个最小任务合同：

- `objective`：本轮必须回答的核心问题；
- `input`：URL、标题或事件线索；
- `scope`：时间、地域和观察尺度；
- `done_gate`：本轮必须新增或核验什么；
- `budget`：最多 12 个有效来源；
- `output`：把研究包增量写到指定文件，只回报状态和路径，不写最终报告。

不要一开始拆出时间线、观点、产业链等多个 Agent；这些是同一事实世界的不同截面。

### 2. 完成事实研究

在任何在线浏览动作前，向用户显示：

> 温馨提示：部分站点对浏览器自动化操作检测严格，存在账号封禁风险。已内置防护措施但无法完全避免，Agent 继续操作即视为接受。

只启动 `news_researcher`，使用 `fork_turns="none"`，向其传递任务合同、研究包路径、任务目录、`<task_dir>/research-delta.json`、必须调用的 Skill 和 [research-packet.md](references/research-packet.md) 的增量合同。

研究 Agent 达到停止条件后必须先写完 `research-delta.json`，再用一条短消息返回 `complete|incomplete + 文件路径`，不得继续扩搜或在消息中复述完整 JSON。Master 看到可解析的增量文件即可结束该线程并继续；消息中的“完成”或“正在写入”不算交付，缺少可解析文件时按下文的交付恢复规则处理。

研究 Agent 必须使用 `$article-research`；该 Skill 按自身契约调用 `$deep-research` 与 `$web-chrome`。Master 不另造搜索流程，也不用搜索摘要代替正文。

把文件中的增量合并进研究包，保存 Agent 的简短回执，然后运行：

```bash
python3 .codex/skills/analyze-news/scripts/validate_packet.py \
  <research-packet.json> --phase research
```

若只是 ID、反向引用或字段形式错误，可在不改变事实含义的前提下修正表示；若缺的是来源、关键事实或反方搜索，则不能由 Master 补写。

### 3. 完成因果与影响分析

只有研究门禁通过，才使用 `fork_turns="none"` 启动 `news_analyst`。向其传递：

- 已冻结的研究包路径；
- `<task_dir>/analysis-delta.json` 输出路径；
- 用户真正要理解的问题；
- 输出增量合同；
- 禁止联网、禁止改写事实、禁止派生 Agent。

分析 Agent 必须把完整增量写入 `analysis-delta.json`，只回报状态和路径。Master 读入后立即结束该线程，再执行后续门禁或补查；消息中的自报状态不替代文件交付。

分析 Agent 必须使用 `$look-think`，把观点写成“主体—结论—因果步骤—成立条件—证据/反证”，把影响写成“直接层—相邻链路层—系统层”。没有真实行业链路时允许标记 `not_applicable`，禁止为了填满栏目虚构影响。

### 4. 有界处理交付失联

可解析的增量文件是唯一完成信号。仅统计子 Agent 自身的新事件，不把 Master 的等待提示当作进展：

1. 子 Agent 报告收敛或准备写入后，若连续 5 分钟既无新事件也无增量文件，只发送一次交付提醒：停止扩展，立即依据已保存材料写入指定文件并校验 JSON。
2. 提醒后再连续 2 分钟无新事件且仍无文件，或线程已经不可通信，结束失效线程。若 `workflow.delivery_recoveries` 为 0，将其改为 1，并只重派一次完全相同的 Agent、任务合同和输出路径；使用现有持久化材料，预算与边界不得重置。
3. 重派线程仍未交付时，标记 `incomplete` 并报告交接故障，不再催促、重派或启动第三个角色。

交付恢复只修复“结果没有落盘”的运行故障，不等于证据补查，不增加 `followup_rounds`，也不得借机联网或生成新事实。回执必须记录原线程状态、恢复原因、`delivery_recoveries` 和最终文件路径。

### 5. 只允许一次定向补查

分析 Agent 可以提出证据缺口。Master 仅在该缺口可能改变以下任一项时发起补查：

- 事件究竟是什么；
- 一条核心因果机制是否成立；
- 影响方向或主要受影响者；
- 对未来走向具有区分力的关键条件。

全流程 `followup_rounds` 不得超过 1。一次补查可包含“研究 Agent 补证 → 研究门禁 → 分析 Agent 局部更新”，但不能扩成新的开放研究主题。

若补查后仍缺关键证据，标记 `incomplete` 并保留分支；不得继续循环，不得用模型常识补成确定结论。

### 6. 执行最终门禁

合并分析增量后运行：

```bash
python3 .codex/skills/analyze-news/scripts/validate_packet.py \
  <research-packet.json> --phase final
```

只有脚本通过，才把状态标为 `complete`。来源达到 12 个只是预算用尽，不代表研究完成；若脚本不通过，交付条件性报告并明确缺口和影响，状态保持 `incomplete`。

## 搜索停止规则

同时满足以下条件才停止事实搜索：

1. 核心主张能够回到来源正文；
2. 时间线覆盖事前、触发和当前；
3. 至少包含原始/官方来源与独立来源；
4. 已主动寻找反方、替代解释或不利证据；
5. 连续两个搜索批次不再改变核心事实、时间线或来源多样性；
6. 没有开放的关键缺口。

新增材料只增加背景而不改变局面时停止，并立即写入增量文件。访问受阻、证据冲突或预算用尽时，也停止继续扩张，但结果必须是 `incomplete` 或保留冲突。

## 最终报告

先给结论，再按问题自然组织，不机械展示内部 JSON。至少让用户看见：

1. **这究竟是什么变化**：一至三段说明事件从什么状态走到什么状态、当前到哪一步；
2. **时间线与已确认事实**：只保留改变理解的节点，区分已发生、已宣布未落地和未知；
3. **主要观点与因果链**：说明谁持何观点、凭什么、在哪些条件下成立、有哪些反证或替代解释；
4. **影响怎样传播**：从直接对象到相邻产业/行业链路，再到系统层；标记证据、推演与不适用；
5. **接下来怎样观察**：给出条件化走向、反转条件、可观察信号、关键未知和直接来源链接。

重要数字保留时间、单位、口径和范围。未来判断使用“如果—那么—可观察信号”，不写成已经发生的事实。

## 禁止事项

- 不把转载数量当作独立来源数量；
- 不把官媒表态自动等同于政策已经执行；
- 不把相关、先后发生或利益一致自动写成因果；
- 不让研究 Agent 给宏观结论，也不让分析 Agent自行联网补证；
- 不在门禁失败时输出“研究已完成”；
- 不用无限循环、动态 Agent 注册表或多层 Master 解决当前任务。
