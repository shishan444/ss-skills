# 三层测试用例设计

## 使命

把需求转换为与业务代码同等重要的测试资产：先形成可审查的测试方案，再产出统一用例契约，使不同测试工具能够被统一选择、调用、回归和判断结果。

始终坚持八项要求：

1. 所有测试用例采用统一语义契约。
2. 用例具备统一自动调用和回归所需的元数据。
3. 按 L1 单元逻辑、L2 业务流程、L3 模拟人类操作三层组织。
4. 覆盖正向、反向和有事实机制的潜在风险。
5. 业务链路通过流程模型实现系统性覆盖。
6. L3 使用 Chrome、Playwright、WebDriver 等工具验证真实操作。
7. 测试方案必须先设计、评审，再进入自动化实施。
8. 测试用例与业务代码共同版本化、评审、运行和维护。

## 强制触发与责任边界

- 任何功能开发、缺陷修复、代码重构、数据或接口迁移、配置与依赖变更，以及其他会改变工程行为或交付结果的工作，都必须调用本 Skill；用户没有主动要求测试，不构成跳过理由。
- 在业务代码实施前，从需求和变更目标形成测试方案与统一用例；在实施完成后，落实并执行适当的 L1、L2、L3 测试，形成当前版本的验证证据。
- “必须调用”表示每项工程变更都必须经过测试责任判断，不表示所有变更采用相同文档规模、审批强度或运行层级；测试深度必须与变更边界和风险匹配。
- “完整测试”指当前需求、业务链路和已识别风险产生的覆盖义务均有用例、条件分支、阻断、不适用或明确风险处置，不指穷举所有输入组合。
- 只做代码解释、状态查询或不改变工程行为的只读工作不强制生成测试；一旦实际修改工程实现，即进入本 Skill 的责任范围。
- 代码写完不等于任务完成。没有完成适当测试执行，或存在未处置的 `FAIL`、`ERROR`、`SKIPPED`、`QUARANTINED`，不得宣称具备交付质量。

## 选择验证深度

触发后先分类，再设计用例。统一的是语义框架和完成标准，不是产物重量：

- **focused**：局部、确定性的规则或实现变更，不跨数据库、网络、消息、权限、部署或真实界面边界，也没有高影响风险。使用精简测试方案和项目原生测试；明确 L2、L3 及不适用类别的理由，不虚构流程模型或浏览器用例。
- **standard**：改变用户可观察行为，或跨 API、数据库、消息、权限、外部依赖等边界。建立正式测试设计、业务流程模型和统一机器清单，执行适用的 L1、L2，涉及界面时执行 L3。
- **critical**：涉及资金、权限、安全、数据不可逆变更、迁移、并发一致性、关键用户旅程、发布或部署门禁。采用完整正式产物、明确审批、目标环境执行证据和剩余风险判断。

任一高风险条件成立就升级到 `critical`；范围或风险无法判断时采用较高档位。实施中发现新的跨层机制或风险时，重新分类并补充设计，不受初始档位限制。

### `focused` 精简契约

`focused` 不是把正式清单改写成一篇长文。设计型任务默认只交付一个不超过 80 行的 `test-design.md`；若保持语义完整需要突破该规模，先重新判断是否应升级为 `standard`。固定使用五部分：

1. 就绪状态、档位理由和设计门。
2. 需求来源、受保护价值及关键未知。
3. L1/L2/L3 与正向/反向/风险的处置矩阵。
4. 参数化用例表：`case_id`、追溯（来源/验证命题/覆盖义务）、单一 `category`、输入分区、刺激、oracle、计划入口和证据。追溯可压缩在一列，但稳定 ID 不得省略。
5. 实施运行计划、未覆盖项及剩余风险。

合并具有相同刺激、oracle 和故障边界的等价输入，不为每个值、每项命题或每项义务拆一条用例。`category` 只能是 `positive`、`negative`、`risk` 中一个；边界、回归、类型等作为标签，不拼接成新类别。语言实现陷阱若已被正向或反向用例检出，不再重复建立风险用例。需求明确声明“无副作用”但实现材料没有出现外部边界时，把它作为所有用例共同不变量，不单独构造依赖探针或虚假测试替身。

## 按需读取参考资料

- `focused` 且层级边界明确时，直接使用本文件的核心规则，不强制加载完整引用文件。
- `standard`、`critical`，或层级路由、业务链路、L3 边界存在疑问时，读取 [references/three-layer-method.md](references/three-layer-method.md)。
- 需要生成、修改或评审正式 `test-cases.json` 时，读取 [references/unified-test-contract.md](references/unified-test-contract.md)，严格使用其中的产物结构和字段。
- 生成正式清单后直接运行 `scripts/validate_test_manifest.py`；除非修复校验器本身，不要为使用它而读取脚本源码。

用户或仓库明确要求正式统一清单时，不得因任务较小而另造格式。

## 输入和事实边界

优先读取用户提供的需求、验收标准、业务决议、缺陷记录、接口、架构和相关代码。区分：

- **已确认**：需求或用户明确给出的目标行为。
- **推导**：由已确认事实必然得到的规则、状态或结果。
- **候选**：有材料锚点，但存在其他合理解释。
- **关键未知**：不同答案会改变预期结果、测试层级或交付判断。

现有代码只能证明“当前怎样运行”，不能自动证明“应该怎样运行”。行业惯例只能帮助寻找问题，不能冒充本项目需求。

输入不足时继续完成不受影响的设计，并将状态设为 `conditional` 或 `blocked`；不得编造断言。只询问会改变核心预期、范围、层级或高风险判断的问题，每轮最多三个。

## 工作流

### 1. 建立最小需求基线

从材料中提取：

- 谁在什么初始状态下执行什么行为。
- 系统必须进入什么目标状态，产生什么用户或业务价值。
- 哪些结果绝不能发生。
- 涉及哪些角色、对象、状态、规则、依赖和界面入口。
- 变更前、变更中、目标状态、失败恢复及长期运行约束。
- 已确认、推导、假设和关键未知分别是什么。

给出就绪判断：

- `ready`：核心预期、边界和观察方式明确。
- `conditional`：存在未知，但可形成互不混淆的条件分支。
- `blocked`：核心预期无法判定或需求存在实质冲突。

### 2. 先形成测试方案

在写具体用例前，先形成并审查测试方案。`focused` 可合并为精简记录；`standard` 和 `critical` 使用完整结构：

1. 受保护价值与测试范围。
2. 角色、对象、状态、规则和依赖。
3. L2 业务流程图：入口、关键节点、守卫边、终态、副作用和恢复路径。
4. 风险链：受保护价值 → 暴露位置 → 触发条件 → 失败机制 → 不利结果 → 观察证据。
5. 验证命题：上下文、刺激、结果、不变量和破坏后果。
6. 三层分工：每项命题的主责层、加固层及不重复理由。
7. 正向、反向、风险三类覆盖义务。
8. 自动化适配器、运行档位、数据控制、清理和证据要求。

测试方案没有通过适用的设计门时，不实现测试代码。用户只要求测试用例时，交付方案和用例即停止，不擅自修改业务代码。

### 3. 设计三层用例

按“能够同时容纳缺陷机制和可靠判定位置的最低成本层级”确定主责层：

- **L1 单元逻辑**：规则、计算、决策、状态转换、不变量及局部错误策略。
- **L2 业务流程**：API、应用服务、真实数据、数据库、消息、权限、外部依赖、事务、补偿和恢复。
- **L3 模拟人类操作**：真实角色通过可见界面完成导航、输入、选择、提交、理解反馈和恢复。

每项覆盖义务必须有一个主责层。只有新增失败机制时才添加跨层加固，不把完全相同的输入和断言复制三遍。每一层必须有用例，或明确记录 `not_applicable` 及原因。

### 4. 覆盖正向、反向和风险

- **正向**：合法条件能形成目标状态和必要副作用。
- **反向**：守卫条件、权限、非法状态、边界或依赖失败能被正确拒绝，且不变量不被破坏。
- **风险**：只验证有材料锚点和连续失败机制的并发、幂等、一致性、安全、性能、时间、兼容、资源或外部依赖风险。

三类都必须被考虑并在方案中处置。缺少某类用例时，必须说明为什么不适用；不要随机枚举错误输入或通用风险清单。

### 5. 系统覆盖业务链路

当 L2 适用时，先建流程模型，再生成 L2 用例。L2 不适用时记录具体边界理由，不创建空洞流程。适用时至少检查：

- 关键入口和业务节点。
- 守卫条件的通过与拒绝。
- 产生独立业务结果的关键边。
- 成功、拒绝、失败和恢复终态。
- 数据写入、事件、通知、审计等必要副作用。
- 真实存在的重复、并发、超时、补偿、重试和最终一致性路径。

“系统性覆盖”指关键节点、边、规则、终态和恢复义务均有明确处置，不指穷举所有数学组合。每个 L2 用例必须引用 `flow_id`。

### 6. 设计模拟人类真实操作

L3 核心动作必须通过用户真实可见入口完成：

- 可用 API 或数据工厂准备前置数据，但不得绕过被验证的核心界面动作。
- 优先使用语义定位，不依赖屏幕坐标、脆弱 CSS 层级或易变文案。
- 点击成功不等于业务成功；同时验证页面状态、持久化结果、必要副作用和禁止结果。
- 记录截图、DOM 或可访问性树、网络、控制台和必要录像证据。
- 区分确定性回归与 Agent 自适应探索。探索发现必须固化成确定性契约后才能进入硬门禁。

无法访问真实页面时仍可完成 L3 用例设计，但必须把运行状态标记为“已设计、未形成有效运行证据”。

### 7. 生成统一产物

根据验证深度交付产物：

- `focused`：默认按“`focused` 精简契约”交付单一测试记录。工程实施任务仍须把实际测试代码与业务代码共同落盘和运行。
- `standard`、`critical`：交付两个相互一致的正式产物：

1. `test-design.md`：供产品、研发和测试共同评审。
2. `test-cases.json`：供执行适配器、回归调度和结果聚合使用。

用户、仓库或既有治理明确要求正式清单时，任何档位都使用双产物。若需要在仓库落盘，优先放入项目已有测试设计目录；没有约定时使用 `docs/testing/<feature>/`。若用户只要求回答，则在回复中给出相应深度的设计和用例摘要，不擅自创建文件。

`test-design.md` 按以下顺序组织：

```markdown
# <功能>测试设计
## 结论与就绪状态
## 需求基线、假设与关键未知
## 范围和受保护价值
## 三层测试策略
## 业务流程模型
## 风险链与验证命题
## 覆盖义务矩阵
## 测试用例摘要
## 自动调用与回归计划
## 未覆盖项、剩余风险与停止判断
## 设计审批
```

`test-cases.json` 必须符合 `unified-test-contract.md`。生成文件后运行：

```bash
python3 <skill-directory>/scripts/validate_test_manifest.py <path/to/test-cases.json>
```

校验失败时修正产物并重跑；不得把校验警告藏在结论中。

### 8. 设置设计门和实施边界

- 所有档位都必须先完成测试设计，再实施相应代码；档位只改变设计重量，不取消设计门。
- 初始 `design_gate.status` 使用 `draft` 或 `blocked`。
- 只有需求、方案和用例经过用户或责任人确认后，才改为 `approved`。
- `approval_required_before_implementation` 必须为 `true`。
- 已获批准的开发方案若明确包含本轮测试设计、执行范围和剩余风险，可同时作为测试设计批准，不重复请求同一决定；出现新需求解释或风险升级时必须重新确认。
- 工程开发任务中，设计获批后从已批准用例生成对应执行适配器，并与业务代码共同实施，不反向篡改业务预期。
- 实现发现需求冲突时退回设计门，不静默选择一个解释。

### 9. 实施测试并验证交付

当本 Skill 因工程开发任务触发且设计门已经批准时，继续完成测试闭环：

1. 将批准的用例实现为项目适用的单元、业务流程和真实操作测试；不只生成文档或计划路径。
2. 根据变更影响和风险运行相关 L1、关键 L2 与必要 L3；发布或部署任务执行相应发布前、部署后门禁。
3. 界面行为发生变化时，使用 Chrome、Playwright、WebDriver 等工具完成真实用户操作并收集页面、网络、控制台和业务终态证据。
4. 严格区分产品失败、测试执行错误、跳过和隔离状态，不以重试、忽略或降级断言制造通过。
5. 发现实现缺陷时回到业务代码修复并重跑受影响测试；发现需求冲突时退回设计门澄清。
6. 交付时报告实际执行的版本、环境、用例集合、结果、证据、未执行项和剩余风险。

无法运行某层测试时，说明缺失的环境或能力及其对交付判断的影响；设计完成不能替代实际验证证据。

## 自动调用与回归要求

统一的是语义和调度，不是强迫三层使用同一个运行器。每条用例都要声明：

- 稳定 `case_id`、来源、验证命题、覆盖义务和层级。
- 明确责任人和 `draft`、`reviewed`、`automated`、`regression_active`、`quarantined`、`retired` 生命周期状态。
- 执行适配器、入口、确定性及运行档位。
- 前置数据、环境、时间、随机性和外部依赖控制。
- 清理方式和证据要求。
- PR、定时、发布前、部署后或探索等运行档位。

运行结果必须区分 `PASS`、`FAIL`、`ERROR`、`SKIPPED`、`QUARANTINED`。只有目标版本、目标环境中的稳定实际执行通过才能成为有效回归证据。

## 回答原则

- 先给就绪结论和最高风险缺口，再给完整设计。
- 说明为什么某项命题属于某一层，以及其他层为何不重复。
- 使用明确、可重复判定的 Given/When/Then/And，不写“功能正常”“操作成功”。
- 一条用例只保留一个主要验证目标，但允许多个共同证明该目标的关联断言。
- 重要遗漏必须显式标记为未覆盖、条件覆盖、阻断或剩余风险。
- 不用用例数量、代码覆盖率或一次浏览器主流程绿灯宣称完整覆盖。

## 完成标准

只有同时满足以下条件，才把本轮测试设计标记为完成：

- 需求基线和当前解释可追溯，关键未知没有被伪装成事实。
- 测试方案先于具体用例形成，设计门状态明确。
- L1、L2、L3 均有用例或有可审查的不适用理由。
- 正向、反向、风险均有用例或有可审查的不适用理由。
- 每项关键验证命题和覆盖义务都有唯一主责层。
- L2 流程模型的关键节点、边、终态、副作用和恢复路径均有处置。
- L3 核心动作明确通过真实界面完成，并声明 Chrome 等执行工具和证据。
- 每条用例具备自动调用、隔离、清理、回归档位和结果判定所需字段。
- 每条用例拥有责任人和生命周期状态，能像业务代码一样进入评审、变更和退役治理。
- 使用正式双产物时，人读设计与机器清单相互一致，`validate_test_manifest.py` 校验通过；`focused` 精简记录则必须保持同等语义要素和可执行入口。
- 未覆盖项、剩余风险和后续实施边界保持可见。

以上条件只证明测试设计完整。对于工程开发与交付任务，还必须同时满足：

- 与变更相关的用例已经实现，或明确记录无法自动化的依据与替代验证方式。
- 要求执行的 L1、L2、L3 测试已在目标代码版本和有效环境实际运行。
- 硬门禁中不存在未处置的 `FAIL`、`ERROR`、`SKIPPED` 或 `QUARANTINED`。
- 涉及界面行为时，已通过真实操作取得用户可见结果和业务终态证据。
- 测试结果能够追溯到当前需求、变更、用例和运行环境。
- 未覆盖项和剩余风险已经明确，不用“测试设计完成”代替“交付验证完成”。
