## 1. 三层证据边界

三层不是三套重复用例，而是三个故障发生和证据观察边界：

| 层级 | 核心问题 | 主要对象 | 典型适配器 |
| --- | --- | --- | --- |
| L1 单元逻辑 | 局部规则本身是否正确 | 计算、判断、状态转换、不变量 | pytest、JUnit、Vitest 等 |
| L2 业务流程 | 组件连接后能否形成完整业务结果 | API、服务、数据库、消息、权限、依赖、补偿 | API runner、集成测试框架、容器环境等 |
| L3 模拟人类操作 | 真实角色能否通过界面完成目标 | 页面、导航、控件、反馈、部署配置、最终结果 | Chrome、Playwright、WebDriver 等 |

横向的安全、性能、可靠性、兼容性、可访问性和资源消耗不是第四层。只有存在事实锚点和失败机制时，才把它们路由到能产生和观察风险的相应层。

## 2. 层级路由方法

对每项验证命题依次判断：

1. 它保护什么用户、业务或系统价值。
2. 破坏它的缺陷最早在哪个边界产生。
3. 哪个位置能够观察业务真值，而不是技术表象。
4. 更低层是否真实包含该失败机制。
5. 更高层是否存在低层不能发现的独立风险。
6. 执行和维护成本是否与风险价值匹配。

主责层是最低成本且具有真实检出力与清晰诊断力的层。加固层只承担新增的连接或交互风险。

示例：同一商品重复加入购物车只增加数量。

- L1 主责商品行唯一和数量转换规则。
- L2 加固接口映射、事务与真实持久化唯一性。
- L3 加固按钮绑定、请求触发和页面展示。

三层保护同一价值，但故障机制不同，因此不是无效重复。

## 3. L1 单元逻辑层

### 必须覆盖

- 合法输入和状态产生目标结果。
- 守卫条件拒绝非法状态转换。
- 会改变结果的等价类、边界值和决策组合。
- 操作成功或失败后关键不变量继续成立。
- 时间、随机、ID、外部 API 和收费服务得到控制。
- 错误被转换为明确业务错误，而不是只检查抛出异常。

### 不得冒充

- Mock 数据库后宣称真实 Schema 或事务已覆盖。
- 只验证方法调用次数而不判断业务结果。
- 测试私有实现细节、框架生成代码或无业务意义的 getter/setter。
- 用大面积快照代替明确断言。

### `layer_detail` 必需字段

- `unit_under_test`：最小稳定业务单元。
- `rule_or_invariant`：被证明的规则或不变量。
- `test_doubles`：替换了哪些依赖及原因；没有则为空数组。

## 4. L2 业务流程层

### 流程家族

只在需求或系统机制存在时选择：

- 主成功流程。
- 合法替代流程。
- 权限、资格、状态或数据拒绝流程。
- 数据库、消息、网络或外部服务失败流程。
- 部分成功后的回滚、补偿、重试或人工接管。
- 重复请求、消息重放和幂等流程。
- 异步中间态、超时与最终一致性流程。
- 并发竞争与唯一性、余额、状态约束。
- 旧数据、旧客户端、Schema 或协议迁移兼容。

### 真实边界原则

- 数据一致性是核心风险时使用真实 Schema 和数据库行为。
- 服务兼容是核心风险时验证真实请求、响应契约。
- 消息机制是核心风险时验证结构、发送、消费和终态。
- 外部服务不可稳定接入时使用契约沙箱、模拟服务器或经验证录制响应，并明确证据边界。

HTTP 200、数据库存在记录或消息已发送都不能单独证明业务成功。断言必须落到业务终态、必要副作用与禁止副作用。

### `layer_detail` 必需字段

- `flow_ids`：引用一个或多个业务流程模型。
- `business_entry`：真实业务入口。
- `end_state`：用例要证明的业务终态。
- `side_effects`：必要或禁止副作用；没有则为空数组并解释。
- `covered_flow_elements`：本用例承接的节点、边、终态和副作用 ID。

## 5. L3 模拟人类操作层

### 核心动作边界

- 使用真实可见控件导航、输入、选择和提交。
- 可用 API 或数据工厂创建前置数据，但核心动作不得绕过 UI。
- 根据页面反馈决定后续操作，不调用隐藏内部函数。
- 同时验证用户可见结果和必要业务终态。
- 验证错误反馈是否准确、可理解且存在恢复路径。

### 交互覆盖模型

```text
角色 × 有意义的页面状态 × 独立作用控件
  → 用户动作
  → 目标页面状态
  → 业务结果或恢复结果
```

不穷举任意点击排列。只有动作顺序会改变页面或业务状态时，才形成独立路径。

### 两种运行模式

- `regression`：角色、前置状态、步骤、定位和判定固定，可进入回归门禁。
- `exploration`：Agent 根据页面状态探索未知路径，只产生发现和候选用例；固化为确定性契约后才能成为硬门禁。

### `layer_detail` 必需字段

- `role`：真实用户角色。
- `start_state`：页面、会话和业务初始状态。
- `core_action_via_ui`：必须为 `true`。
- `tool`：Chrome、Playwright、WebDriver 或实际执行工具。
- `mode`：`regression` 或 `exploration`。
- `locator_strategy`：语义定位方式。
- `observations`：页面、业务、网络、控制台和证据观察点。

## 6. 正向、反向和风险

### 正向

证明合法条件能够形成目标状态。覆盖真正改变规则分支的代表性等价类，而不是只写一个快乐路径。

### 反向

针对明确守卫条件、不变量或失败契约：

- 无权限或不具资格。
- 非法状态转换。
- 明确输入边界。
- 依赖拒绝、错误或不可用。
- 失败后原状态、不变量及禁止副作用。

反向测试不是随机传入错误数据。

### 潜在风险

风险必须形成完整链：

```text
受保护价值
  → 暴露位置
  → 触发条件
  → 连续失败机制
  → 不利业务状态
  → 可观察证据
```

并发、安全、性能、时间、资源、兼容和依赖只是搜索方向。没有需求、架构、代码入口、历史缺陷或事故作为锚点时，只能记录为探索候选，不能伪造确定性预期。

## 7. 系统性链路覆盖

每个核心业务流程先表达为有向状态图：

```text
初始状态
  → 入口与守卫
  → 中间业务状态
  → 依赖和副作用
  → 成功 / 拒绝 / 失败 / 恢复终态
```

从图中生成覆盖义务：

- 每个关键节点是否可达。
- 每条关键边是否被触发。
- 每个守卫的通过和拒绝是否被验证。
- 每个独立终态是否可明确判定。
- 必要副作用是否发生且只发生规定次数。
- 禁止副作用是否没有发生。
- 失败后不变量是否保持。
- 补偿、重试、恢复或人工接管是否可达。

用例清单不能代替流程模型。`flow_models` 是覆盖分母，L2 用例通过 `flow_ids` 和覆盖义务证明对分母的处置。

## 8. 去重与停止条件

新增用例至少增加一项独立价值：新需求、新规则、新状态、新流程边、新风险机制、新层级故障边界、历史缺陷检出力或更低成本替代。

若两条用例具有相同前置、刺激、判定和故障边界，应合并或参数化。高层只重复低层规则、没有连接或交互风险时，应下沉或删除。

设计可以停止，当：

- 关键需求、规则、状态、流程、权限、依赖和交互都形成覆盖义务。
- 关键义务都有主责层和用例，或明确为条件、阻断、风险接受或不适用。
- 正向、反向、风险三类均已处置。
- L2 关键流程分母闭合，L3 核心旅程可通过真实入口验证。
- 新增候选用例不再增加独立故障检出边界。
- 剩余风险和责任人保持可见。

“用例很多”“代码覆盖率 100%”“浏览器主流程通过一次”都不是停止依据。
