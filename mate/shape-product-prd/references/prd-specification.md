## 1. 文档原则

- 让产品、设计、研发、测试、运营对同一需求形成相同理解。
- 保持“问题 → 目标 → 方案 → 需求 → 验收 → 指标”可追溯。
- 根据产品类型裁剪章节；不适用时写明原因，不为完整外观虚构信息。
- 将用户事实、外部证据、产品建议、工作假设和待确认事项分开。
- 使用可观察、可判断、可测试的语言，避免“友好、快速、智能、灵活”等无标准形容词。
- 先写决策和规则，再写界面细节；PRD 不替代视觉稿和技术设计。

## 2. 完整 PRD 结构

### 0. 文档信息

- 产品或项目名称。
- 文档版本、状态、日期和负责人。
- 本版变化摘要。
- 关联材料和关键决策记录。

### 1. 执行摘要

用一页以内回答：

- 为谁解决什么问题。
- 为什么现在值得做。
- 建议采用什么方案。
- 当前范围和明确非目标。
- 最大收益、风险和待决策事项。

### 2. 背景与问题定义

- 触发背景和现状。
- 用户当前行为与替代方案。
- 核心阻碍、后果和问题证据。
- 表面诉求与本质需求的区别。
- 已知事实、推断和待验证假设。

没有用户研究或业务数据时如实说明，不虚构“调研显示”。

### 3. 产品目标与非目标

为每个目标提供可观察的成功证据。明确本期不优化、不服务或不承诺的内容及原因。

### 4. 用户与场景

- 首要用户、次要角色和不服务人群。
- 核心任务、触发条件、使用环境和限制。
- 端到端场景或用户故事。
- 角色之间的权限、利益或协作关系。

用户故事必须连接真实场景与结果，不能只是“作为用户，我想点击某按钮”。

### 5. 产品原则与关键决策

列出指导后续取舍的原则、已确认决策、主要替代方案及未选择原因。

### 6. 范围与版本

- 本期范围。
- 后续范围。
- 明确排除项。
- MVP 要验证的核心假设。
- 发布阶段、灰度或回退边界（适用时）。

### 7. 总体方案

引用或内嵌产品呈现蓝图中的：

- 产品定位与价值主张。
- 架构、核心对象和角色关系。
- 核心用户流程。
- 页面、模块、触点或 API 概览。
- 关键状态迁移。

### 8. 详细功能需求

先用清单建立追溯关系：

| ID | 需求名称 | 用户价值或目标 | 优先级 | 依赖 | 状态 |
|---|---|---|---|---|---|

再按“单项需求规格”展开关键需求。编号保持稳定；删除需求时标记废弃，不把旧编号静默复用。

### 9. 业务规则

集中定义跨多个需求复用的规则：

- 资格、额度、时间、顺序、去重和冲突规则。
- 角色、权限、审批和可见范围。
- 对象状态及允许的迁移。
- 创建、修改、撤回、删除、过期和恢复。
- 通知、审计或人工介入条件。

使用决策表或状态表消除复杂条件歧义。

### 10. 数据、埋点与指标

- 核心对象与必要数据，不直接替代详细数据模型。
- 关键事件、触发时机和必要属性。
- 目标指标、用户结果指标和护栏指标。
- 基线、观察窗口和分析口径；未知时说明建立办法。
- 数据最小化、保留和敏感性要求。

### 11. 非功能要求

只保留适用项目，并提供可验证标准：

- 性能与容量。
- 可用性、可靠性和恢复。
- 安全、隐私和合规。
- 无障碍与包容性。
- 兼容性、国际化和本地化。
- 可观测性、审计与运营支持。

无法确定数值时记录负责方和确认节点，不随意编造行业标准。

### 12. 依赖、风险与应对

记录外部系统、团队、数据、政策、运营或技术前提。对每个高影响风险说明发生条件、影响、预防或回退方式。

### 13. 发布与运营

适用时定义：

- 发布前置条件和检查项。
- 数据迁移、灰度、开关和回退。
- 客服、运营、内容或审核准备。
- 上线后的观察周期、异常阈值和决策动作。

### 14. 验收与完成定义

汇总关键验收场景、非功能验收、上线门槛和不在本次验收范围内的内容。

### 15. 假设与未决事项

每项注明：

- 当前暂定判断。
- 为什么尚未确认。
- 不同答案影响什么。
- 建议如何验证或由谁决定。
- 最晚确认时间或阶段。

## 3. 单项需求规格

关键需求按以下结构展开：

```markdown
### [REQ-001] 需求名称

**目的与用户价值**
[它解决哪个问题、支持哪个目标。]

**角色与前置条件**
[谁在什么条件下可以使用。]

**触发与主流程**
1. ...

**业务规则**
- ...

**页面或交互要求**
[必要的信息、动作、反馈；不规定无依据的视觉细节。]

**状态与异常**
- 空状态：
- 加载或处理中：
- 成功：
- 输入无效：
- 失败与重试：
- 无权限：
- 中断与恢复：

**数据、权限与埋点**
- ...

**依赖与风险**
- ...

**验收标准**
- ...
```

简单、低风险需求可以压缩，但不得省略会导致不同实现理解的规则或异常。

## 4. 验收标准

优先使用可验证场景：

```gherkin
场景：符合条件的用户完成核心任务
假如 [明确的角色、数据与前置状态]
当 [用户动作或系统事件]
那么 [可观察结果]
并且 [必要的状态、数据、通知或权限变化]
```

至少覆盖：

- 核心成功路径。
- 关键边界值。
- 无效输入或不满足条件。
- 权限差异。
- 重复操作、并发或幂等性（适用时）。
- 第三方失败、超时和恢复（适用时）。
- 状态迁移和数据结果。

不合格：“页面加载迅速”“操作简单”“系统正确提示”。

合格：“在正常网络和约定数据量下，主要内容在既定性能阈值内可操作；超时后保留已输入内容并提供重试。”具体阈值应由产品目标、技术评估或现有基线确定。

## 5. 质量门槛

### 价值一致性

- 每个 P0/P1 需求能否追溯到一个目标或必要约束？
- 删除该需求会破坏哪个用户价值闭环？
- 是否混入只因竞品拥有或内部偏好而存在的功能？

### 逻辑完整性

- 角色、对象、规则、流程和状态是否使用一致术语？
- 正常、空、错误、无权限、中断和恢复是否按风险覆盖？
- 跨章节的范围、指标和验收是否互相支持？

### 可实现与可验收

- 研发能否判断输入、处理规则和输出？
- 设计能否判断信息、动作、反馈和状态？
- 测试能否在不猜测产品意图的情况下编写用例？

### 事实边界

- 是否把假设或建议伪装成研究结论？
- 是否存在未经验证的精确数据、技术承诺或合规判断？
- 所有高风险待确认项是否可见？

### 决策可理解

- 非专业用户能否理解推荐方案为什么优于替代方案？
- 是否说明了范围取舍、机会成本和改变判断的条件？

## 6. 评审既有 PRD

按以下顺序评审：

1. 给出产品负责人总判断：可继续、需补全、需重构或不建议推进。
2. 检查文档解决的是本质问题还是预设功能。
3. 按影响列出 3～7 个最高优先级缺口，不先纠结措辞。
4. 说明每个缺口为什么重要、不修正会造成什么后果。
5. 给出推荐修订和替代方案取舍。
6. 更新受影响的目标、流程、规则、指标和验收，不只修改单个段落。
7. 完成质量门槛检查，保留仍未解决的风险。

## 7. 版本与变更

- `v0.1–v0.x`：探索稿，允许存在明确标记的关键假设。
- `v1.0`：问题、范围和关键规则已批准，可进入正式设计与技术评审。
- 后续版本记录新增、修改、删除、影响范围和替代决策。

变更摘要使用：

| 类型 | 内容 | 原因 | 影响章节或需求 | 后续动作 |
|---|---|---|---|---|

任何变更都检查需求编号、流程、规则、数据、指标和验收标准是否需要同步更新。
